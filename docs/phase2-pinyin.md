# Phase 2 · 离线拼音表：量过之后决定不做

结论先放这里：**这条不是性能优化，实测之后降级为「按需触发」**。
当初把它列进 Phase 2 的依据是「运行时字典 = 慢」这个直觉，量完发现不成立。

## 实测数据（2026-10-06，本机 Chrome + Node 24）

### 字典在产物里占多少

`packages/tools/src/pinyin/get.ts` 引的是 `pinyin/lib/web-pinyin.js`，它只带 `data/dict-zi-web.js`。

| 项 | 值 |
|---|---|
| 打进包的字典（在 `vendor-*.js` 里，字符 102343→144317） | 92,161 B raw / **62,029 B gz** |
| 占 `vendor` chunk | **41.3%** |
| 占全部 JS 产物 gzip | **16.5%**（JS gz 合计 376 KB） |
| `node_modules/pinyin` 全量 | 3.9 MB |
| 其中 `phrases-dict.js` 1.9 MB、`dict-zi.js` 1.4 MB | **没进包**：`get.ts` 用 web 变体，且没开 `segment` |

### 运行时反解有多贵

`web-pinyin.js` 的 `buildPinyinCache` 把「拼音 → 一串字」在浏览器里反解成「字 → 拼音」，
20,855 个键，模块加载时、主线程上、应用能渲染之前跑完。

用 CDP `Emulation.setCPUThrottlingRate` 在真 Chrome 里实测这段：

| CPU 节流 | 耗时 |
|---|---|
| 1×（桌面） | **3 ms** |
| 4× | 16 ms |
| 6×（约等于中低端手机） | **33 ms** |

Node 侧 `require('pinyin/lib/web-pinyin.js')` 15 ms。

### 预生成反而更大

| 方案 | gzip |
|---|---|
| 现状（拼音→字 分组，运行时反解） | **62,029 B** |
| 预生成「字→拼音」JSON | 81,334 B |
| 预生成紧凑连写表 | 79,117 B |

现在这个编码本身就是好压缩：1,898 个拼音键，每个键挂一串共享该读音的字
（`āi:"哎哀埃娭溾嗳銰锿噯諰鎄"`）。摊平成 2 万条一对一映射等于把压缩拆开，**多花 17–19 KB gz**。

### 唯一能省体积的做法，以及它的代价

字典里有 20,855 个字；本站词库（26,359 条成语 + 3,401 条多音）实际只用 **4,777** 个字，
**16,079 个字词库从没用过**。只按词库生成表：**17,640 B gz**，省 44 KB gz（约整站 11%）。

代价：`checkValidIdiom(word, strict)` 在**默认的非严格模式下永远返回 true**，用户可以输入任意四个汉字。
字典外的字现在原样返回（实测 `𠀀` → `"𠀀"`、`㰀` → `"㰀"`），砍掉之后这类输入没有读音可比对。
词库内的字是 100% 覆盖的（实测「词库用到但字典里没有的字」为空）。

## 真正的收益只有两条

1. **去掉一个依赖**：少一个第三方运行时依赖、少一个 supply chain 面、`npm install` 少 3.9 MB。
2. **读音变成站内可勘误的数据**：现在某个字读音错了，只能往 `polyphones.json` 里**逐条成语**打补丁；
   如果读音本来就是我们的数据文件，就能像 `src/data/new.txt` + `npm run update` 那样逐字改、能 diff、能写测试。

## 触发条件（满足任一条再动手）

- 真的遇到某个字读音错了、需要逐字改 —— 那时顺带就把依赖去掉了。
- 或者决定把非严格模式收紧成「必须是词库里的成语」—— 那时 17 KB gz 的表就是纯赚。

否则现在动手是**负收益**：要么包变大 17 KB，要么牺牲任意汉字输入的自由度，换来 33 毫秒。

## 如果真要做，正确的做法

不是「预生成反解表」（那更大）。是：

1. 保留「拼音→字」的分组编码，只是改成**自己生成**（构建期脚本，产物 checked-in，可 diff 可测试）；
2. 只覆盖词库用到的 4,777 字；
3. 给词库外的字留一个显式 fallback（照现在的行为原样返回），而不是让它静默失配。
